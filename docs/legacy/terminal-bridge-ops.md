# [已废弃] 终端桥与本地作业规程

> 来源：Notion 温棚旧终端桥遗留页（《[已废弃] 终端桥与本地作业规程》）
> 状态：已废弃，仅作历史参考
> 当前现行架构：Notion 薄中心与工具驾驶舱 + GitHub MCP / PR 流
> 迁移日期：2026-05-18

> 这是终端桥的旧操作规程。有本地手的执行位（克）曾经进场必读；现已退出现行架构。

## 1. 进场接缝

1. **必读交接**：看 `终端` 底部交接槽。非空必须汇报，接手或忽略需给明理由。下个窗口进场时自己读交接槽，不需要谷转述。
2. **寻可用车道**：查看终端面板，挑选 A/B/C/D 其中一条「可用」车道。

## 2. 槽位与并行规则

- **默认并行**：每条独立命令占一槽。
- **例外串行（单槽）**：改同一文件、动 `.git` 操作、必须串行。**单槽操作必须在面板说明理由**。
- **波峰槽（17-20）**：仅当某主线 4 槽全满时临时加宽借用。标明「波峰归属」，任务完成立即释放，不可独占。

## 3. 停顿与红线

写完槽位立即**停下**，等待谷轻触「继续」。**禁止主动轮询或假装看结果**。

**遇到以下情况，绝对停下问谷：**
- 越界、状态不可测、接手边界不清。
- 任何**不可逆 + 多元**选择。
- 命中安全红线。
- Git 状态不干净、冲突、非 fast-forward 变更。

## 4. 闭环与释放标准

代码/文档写入 → 本地测试/检查 → `git diff --check` → `commit/push` → 释放车道。

未闭环若需中断，将状态留于**交接槽**。

## 5. 八大交规（2026-05-11 三方审查定稿）

### ① Git 独占终端一

所有改变代码树状态的操作（`git add`、`commit`、`push`、`checkout`、`merge`、`rebase`）**只在终端一串行执行**。其他终端只许 `git status`、`git log`、`git diff` 等只读操作。

### ② push 必挂车牌号

所有 `git push` 命令必须尾挂 `&& git rev-parse HEAD`，从回填中拿到 Commit Hash。

- 后续验证用 GitHub 文件读取 + hash 击穿缓存。
- **严禁**用 GitHub search 验证刚 push 的代码。

### ③ 串联必带 STEP 标记

`&&` 复合命令必须用 `echo` 插入步骤分隔符：

```sh
echo "=== STEP 1: checkout ===" && git checkout main && echo "=== STEP 2: commit ===" && git commit -am "update" && echo "=== STEP 3: push ===" && git push && echo "=== STEP 4: hash ===" && git rev-parse HEAD
```

### ④ push 前必确认

执行 `git push` 前，先在另一个终端跑 `git diff --stat HEAD` 或 `git log --oneline -3` 确认即将推送的内容。

### ⑤ 删除先探测（Dry-Run 原则）

任何涉及**批量删除**或**批量覆盖**的命令：

- **第一轮**：只跑探测命令，输出待删文件列表。
- **第二轮**：才执行实际删除或覆盖。
- **严禁第一轮直接执行破坏性命令。**

### ⑥ 验证就近

- **刚写的文件** → 终端 `cat file.md` 回填验证。
- **刚 push 的文件** → GitHub 文件读取 + hash 验证。
- **历史 / 全局结构** → GitHub search 或终端 `git log` / `find`。
- **本地全景** → 终端 `git log --all --graph --oneline`。

### ⑦ 交接追加制

交接槽不再覆盖写。每次交接**带时间戳追加新段落**，旧段落不删。进场者只看最新一段。谷定期清理历史。

### ⑧ 领牌再动手

进场第一步看终端主页顶部「终端领用牌」，领一条空闲车道并改写状态。未领牌不写终端。

## 6. 老电脑值守机与命令分档（2026-05-13）

### 6.1 值守机分工

- **老 M1**：Notion 自动继续值守机。插电、保持目标 Notion 对话框前台、运行 watcher。
- **新 M5**：主力工作机。默认不跑 watcher。
- **唯一性规则**：同一时间只允许一台电脑运行 watcher，避免重复读取、重复回填、重复发送「继续」。

### 6.2 自动继续判断

- 收到「继续」后，先读自己车道对应终端的最新回填，再判断下一步。
- 连续收到「继续」不等于 watcher 卡住；更可能是老电脑已经执行完并自动回来了。
- 不要因为聊天侧反应慢，就提前判定本地命令未被吃掉。

### 6.2.1 两种唤醒必须分清

**自动门铃**：对话里只出现「继续」两个字，默认是本地 watcher 在某个 job 完成、失败或需要唤醒 AI 后打回来的门铃。克的动作是：读状态块 → 读自己车道终端 → 判断 job 与 `nextAllowedAction`。

**谷主动进场**：谷主动说话、补充判断、截图、纠正、催促、问“你需要我做什么”、或要求克说明需要帮助时，这不是自动门铃。克要把它当成谷正在进场协作。

**克找谷**：只有遇到不可逆选择、权限/账号/登录、付款/注册、删除/覆盖、Git 脏状态归属不清、多个可行路线需要谷裁决、或 `nextAllowedAction = ask-gu` 时，克才主动找谷。

一句话：**「继续」是门铃；谷说话是进场；克找谷是请求裁决或协助。三者不能混成同一种压力。**

### 6.3 命令速度分档

实测基线来自老 M1 值守机（2026-05-13）：

- `echo` / 小文件写读 / Python 小脚本：几十毫秒级。
- `git status --short --branch`：约 2 秒。
- `git ls-remote`：约 5 秒，受网络波动影响。
- 从 Notion 写入到 watcher 开始执行：本轮约 43 秒。

读取节奏：

1. **S 档：瞬时命令**：收到「继续」后等 **5～10 秒** 再读终端。
2. **M 档：仓库读命令**：收到「继续」后等 **10～20 秒** 再读终端。
3. **N 档：网络命令**：收到「继续」后等 **20～45 秒** 再读终端。
4. **L 档：长任务**：依赖 `⏳ 执行中` 回执和 STEP 标记，不靠聊天里的「继续」猜状态。

### 6.4 自动继续实现约束

- 当前可靠路径是剪贴板粘贴：`set the clipboard` → `Cmd+V` → `key code 36`。
- 不再用 AppleScript 直接 `keystroke "继续"` 输入中文。
- 该方案会短暂占用剪贴板；文本剪贴板会尝试恢复，非文本剪贴板不保证完整恢复。

## 7. 异步回环与异常排查（2026-05-14）

### 7.1 基本事实：终端桥不是同步 shell

终端桥是一条异步回环，不是「写入命令后立刻得到结果」的同步 shell。

一次命令至少经过这些节拍：

1. AI / 用户把 `$ command` 写入 Notion 终端页。
2. Notion 页面写入被远端保存，`last_edited_time` 发生变化。
3. watcher 轮询到槽位变化，读取页面块。
4. watcher 把 `$` 改成 `⚡`，追加 `⏳ 执行中` 回执。
5. 本地 shell 执行命令。
6. watcher 把命令块改成 `✓` / `✗`，追加 output。
7. watcher 触发自动继续，把「继续」送回 Notion 对话。
8. AI 下一轮读取终端页，判断是否闭环。

其中任何一步慢、失败、被 Notion 同步延迟、被页面格式化改写，都可能让聊天侧看到「无变化」。**无变化不等于未执行。**

### 7.2 回填很重要，但回填不是唯一事实

必须区分四种状态：

- **未认领**：页面仍是 `$ command`，没有 jobId，没有 `⏳`。
- **已认领未执行**：命令块已变 `⚡`，但没有 shell 日志或输出。
- **已执行未回填**：本地文件 / Git 状态已变化，但 Notion 页面仍未显示 `✓` / `✗`。
- **已回填未被 AI 看见**：页面已有 `✓` / `✗` 和 output，但对话侧还没读到最新内容。

排查顺序不是「重写命令」，而是「确认状态落在哪一层」。

### 7.3 连续“继续”不是催促

自动继续脚本发来的「继续」只表示本地 watcher 认为某个动作完成或需要唤醒 AI。它不是谷在催，也不意味着必须立刻写入下一条命令。

### 7.4 已知异常面

- **watcher 未运行**：终端页长期停在 `$`。
- **watcher 没扫到槽位**：`$` 长期不变，但 watcher 活着。
- **已认领但未执行**：命令块变 `⚡`，有 `⏳` 或 jobId，但无 shell 输出。
- **shell 已执行但回填失败**：本地文件或 Git 已变，Notion 仍无 `✓` / `✗`。
- **Notion API 超时 / 429 / 5xx**：watcher 本地报 `fetch failed` 或重试耗尽。
- **Notion 格式化污染命令**：heredoc、三引号、fence 被改写。
- **旧 `$` 块抢先**：新命令写了，但 watcher 执行上方旧命令。
- **自动继续太早**：AI 还没看到稳定回填就被唤醒。
- **自动继续失败**：Notion 不在前台、窗口标题不匹配、剪贴板失败。
- **重复 watcher**：多台机器同时读写、重复回填、重复继续。
- **Git 状态异常**：index.lock、非 fast-forward、dirty tree。

### 7.5 排查顺序

当命令没有按预期回填时，按这个顺序摸，不许跳到重写：

1. **读槽位**：确认最新块是 `$`、`⚡`、`✓` 还是 `✗`。
2. **找 jobId**：有 jobId 先查 job；没有 jobId 才判断为未认领。
3. **查 watcher**：确认 `node watch.mjs` 和 `caffeinate` 是否仍在。
4. **查本地事实**：对文件任务看目标文件；对 Git 任务看 `git status` / `git log`；对网络任务看远端验证。
5. **查 Notion 写入**：确认是命令没执行，还是执行了但 Notion patch / append output 失败。
6. **补证据**：必要时截图或写本地 pending queue。
7. **最后才重投**：只有确认「未执行」且不会造成重复副作用时，才允许重写命令。

### 7.6 自动继续必须变成“稳定后继续”

后续改造目标：

- `nudgeNotionContinue()` 只在以下条件同时满足后触发：
	1. 命令块已写成 `✓` / `✗`。
	2. output 已成功 append。
	3. watcher 重新读取或确认 Notion 写入已可见。
	4. job ledger 写入 `finishedAt`、`status`、`lastError` / `summary`。
	5. 已过最小冷却时间。
- 如果 Notion 写入失败，不自动继续；写入本地 pending queue，并在 dashboard / 状态页显示。
- 自动继续文本只是唤醒信号；AI 收到后必须先读状态，不得直接写下一条命令。

### 7.7 克的操作红线

- 不用「更多写入」解决「状态不清」。
- 一个 job 未判定前，不投第二个同类 job。
- 看到连续「继续」先当作自动化脚本回声，不当作谷催促。
- 页面历史乱时，先收束可观测状态，再执行新任务。
- 任何时候都要区分：**命令执行状态、Notion 回填状态、自动继续状态、AI 已读状态**。

### 7.8 让“继续”退回最后一层，而不是催命符

「继续」两个字只能负责唤醒，不能负责承载状态。真正应该可见的是：**为什么继续、哪一个 job 继续、当前卡在哪一层、是否允许继续推进。**

最小可见化字段：

```text
jobId
lane
slotPage
commandHash
status
phase
createdAt
claimedAt
startedAt
lastHeartbeatAt
finishedAt
notionPatchAt
outputAppendAt
continueEligibleAt
continueSentAt
continueReason
retryCount
lastError
unknownStateNote
screenshot
nextAllowedAction
```

`phase`：

```text
notion-written
watcher-detected
claimed
running
shell-finished
output-written
stable-confirmed
continue-sent
ai-read
blocked
unknown-loop-state
```

`nextAllowedAction`：

```text
read-status-only
wait
inspect-watcher
inspect-local
inspect-notion
retry-safe
do-not-retry
ask-gu
```

一句话：终端桥已经能跑，但它是异步系统。异步系统的第一原则不是快，而是可观测、可判定、可恢复。

## 8. 病号节律与夜间队列

> 谷累了、病了、说不出话了——这不是异常，是正常节律。节律下的系统行为不依赖谷实时在场。

**单一可逆夜间队列**
- 骨架、成稿、研究素材整理、搜索、垫文字 → 可进夜间队列自动跑
- 执行规则：自动跑，做完写状态，不唤醒谷
- 产物落在草稿层，谷醒后回溯过目

**二元在场冻结**
- 结撰的读者诊断、骨架审查、终稿放行 → 不进队列
- 病号档谷醒后确认 → 不进队列
- 冻结产物进交接槽，等谷有力气时自己看

**二元不可逆绝对冻结**
- 发布、花钱、删无备份、改公共分支、push影响他人 → 不排队、不夜间跑
- 睡前说"明天发" → 冻到明天谷醒后确认再发
- 任何异常直接冻，不 retry

## 9. 流转判断（四象限出口协议）

> 不重复终端桥怎么跑、值守机怎么轮询、GitHub 怎么验证。只回答：产物/指令离开当前对话时，自动走还是等人？卡了怎么办？

| 四象限 | 自动流转 | 冻结等签 | 卡壳降级 |
|---|---|---|---|
| **单一可逆** | ✅ 直接做，做完写状态 | — | 超时/异常 → 写交接槽，**不问人** |
| **多元可逆** | ✅ 自动跑，保留吵架疤 | — | 异常 → 冻结当前环节，写状态块 |
| **二元在场** | — | ❄️ 冻结，产物进交接槽 | **不问**，等谷主动看 |
| **二元不可逆** | — | ❄️ 冻结，**不进队列** | 任何异常 → 直接冻，**不 retry** |
