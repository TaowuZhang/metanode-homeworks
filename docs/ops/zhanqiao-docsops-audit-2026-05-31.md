# 栈桥 × docs/ops 审计 v0 · 2026-05-31

对象：Notion《栈桥 · 对外折射面》与 GitHub `docs/ops/` 发布 / 展示 / Web / 分发文档。

执行位：Notion 位克；同时使用两套方法：

1. 《审计》技能：覆盖图 → 缺陷清单 → 必要时落库。
2. 当前空间分流法：活现场 / 沉地层；定义 → 职责 → 条件；第一跳 + 居留权。

边界：本文件只诊断，不修复栈桥页和 docs/ops 正文。

---

## 0. 一句话结论

栈桥与 `docs/ops/` 的大方向是对的：

> 栈桥留 Notion，作为公共接口与外显方向的活入口；`docs/ops/` 留 GitHub，作为发布、展示、Web、分发、发布包与静态数据的操作地层。

当前主要问题不是错放，而是两处需要更清楚的接线：

1. 栈桥对“真实桥桩”的触发条件仍偏薄。
2. `docs/ops/` 文件之间已经形成实际管线，但缺一张轻量入口索引，导致 Notion 栈桥指过去以后，未来克仍要在目录里摸索。

## 2. 用“活现场 / 沉地层”重判

| 对象 | 应留 Notion | 应留 GitHub |
|---|---|---|
| 栈桥 | 公共接口活入口、外显方向、回声入口、真实桥桩列表 | 不放主体；只在需要时由 GitHub 文档引用 |
| docs/ops | 不应复刻进 Notion；Notion 只留指针 | 发布管线、Web 结构、静态数据、发布包、平台适配、试运行记录 |
| Notion 公共入口 | 栈桥可留入口和当前状态 | `docs/ops/notion-public-entry.md` 留结构草案和操作规格 |
| Web 首页 | 栈桥留方向和真实站点指针 | `personal-display-and-web.md`、`web-static-data.md`、`web-issue-zero-*` 留实现与试运行文档 |
| 社交分发 | 栈桥留触点与回声判断 | `distribution-map.md`、平台外手文档留操作边界 |
| 发布包 | 栈桥留“是否有发布包 / 出土前托盘”的方向 | `publishing-package.md` 等留规格、字段与生成流程 |

判断：当前分工成立。

## 3. 缺陷清单

### D1 · 栈桥“真实桥桩”触发条件仍偏薄

- 位置：Notion《栈桥 · 对外折射面》“出口判准 / 待接入”。
- 原文关键句：出现具体公共页、站点、发布对象或展示包时，才接成真实桥桩。
- 未达成判据：定义可观测 / 工作流清晰。
- 问题：什么算“具体”？是 URL、页面标题、GitHub 文件、发布包路径、社交账号，还是外部反馈源？当前句子方向对，但执行时仍需克临场猜。
- 判定：轻缺陷。不会导致结构错放，但会导致桥桩接入时标准漂移。
- 建议后续处理：栈桥页可补一张“真实桥桩最小字段表”：对象、外显形态、内部主源、是否可公开、回声如何回收、下一次判断点。

### D2 · docs/ops 缺少轻入口索引

- 位置：GitHub `docs/ops/` 根目录。
- 原文关键状态：目录中已有多份文档，但没有 `README.md` 或等价入口。
- 未达成判据：渐进式披露 / 描述即路由。
- 问题：`distribution-map.md` 实际承担总图，但目录层没有明示“先读它”。未来克从栈桥跳到 `docs/ops/` 时，仍要扫目录猜入口。
- 判定：中缺陷。不是内容错，而是入口路由缺口。
- 建议后续处理：新增 `docs/ops/README.md`，只做极薄索引：先读 distribution-map；公共 Notion 读 notion-public-entry；个人展示 / Web 读 personal-display-and-web；发布包读 publishing-package；Web 数据读 web-static-data；第零期读 web-issue-zero-brief。

### D3 · `publishing-package.md` 明显未完成

- 位置：`docs/ops/publishing-package.md`。
- 原文关键句：`## 路径 / 建议生成：` 后正文停止。
- 未达成判据：先定义成功 / 工作流清晰 / 示例驱动。
- 问题：`distribution-map.md` 指向发布包规格，且多处把发布包作为“出土前托盘”；但规格文件本身只有定位和路径开头，没有字段表、示例、成功判据。
- 判定：中缺陷。发布包在体系中位置重要，但主规格未完成，会导致“发布包”成为漂亮名词而不是可执行对象。
- 建议后续处理：补最小字段表即可，不必大写：source_id、title、body、summary、platform_notes、risk_check、assets、status、created_at、human_check_required。

### D4 · Notion 栈桥与 docs/ops 的关系成立，但缺少反向索引

- 位置：栈桥页“与 Git / 沃壤的关系”与 `docs/ops/`。
- 原文关键句：发布与展示的主源若需要版本化、构建、静态数据或分发流程，应回 Git / 沃壤，尤其是 `docs/ops/`。
- 未达成判据：反馈回路 / 描述即路由。
- 问题：Notion 指向 `docs/ops/`，但 `docs/ops/` 没有反向说明“Notion 栈桥只保留桥头与回声，不复刻本目录”。两边关系靠读者理解，没有双向接线。
- 判定：轻缺陷。
- 建议后续处理：若新增 `docs/ops/README.md`，加一句反向关系即可。

### D5 · 体感信号：栈桥“回声回收”目前像概念，还没有最小记录形态

- 位置：栈桥页“公共回声回收到内部判断里”。
- 体感：这句是对的，但还没有说明回声回收到哪里：对话、潮池、项目、摩擦沉积床、栈桥页，还是 GitHub 文档。
- 未达成判据：体感信号 / 反馈回路。
- 判定：轻缺陷，等真实外部反馈出现再处理更合适。
- 建议后续处理：暂不改；等第一次真实公共反馈出现时，再决定是否需要“回声最小记录格式”。

判定：部分通过，入口和发布包规格需补。

## 5. 我的方法补充判断

用当前空间分流法看，最小处理顺序应是：

1. 不改星盘。
2. 不把 docs/ops 复刻到栈桥。
3. 栈桥只补“真实桥桩最小字段表”。

5. 回声回收先等真实触发，不预造系统。

也就是说：这里不是结构性错位，而是**接线缺口**。
