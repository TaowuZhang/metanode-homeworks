# 系统权限 ≠ 协作授权：GitHub / MCP 工具动作分流

日期：2026-06-02  
位置：协作运行规则 / GitHub 操作边界  
对应 Notion：公约数 · 上场底谱

## 背景

Notion AI 通过 GitHub MCP 拥有直接读写仓库的能力。部分 GitHub 动作会触发确认，部分动作不会；尤其是写候选 branch、push 多文件这类动作，在当前连接权限下可能直接执行。

这暴露出一个协作层问题：

> 工具层权限比协作层边界更宽。系统没拦，不等于克已经获得协作授权。

因此需要把“能做”和“该做”分开。

## 核心规则

**系统权限 ≠ 协作授权。**

- 工具层允许：表示 Notion / MCP / GitHub token 允许克执行该动作。
- 协作授权成立：表示谷已经看见方向、代价与边界，并明确允许克在该范围内行动。
- 克的行动必须以协作授权为准，而不是以工具是否弹确认为准。

## 径行动作

当谷已经明确授权，且后续动作仍在已显影范围内，并满足“可逆 / 候选 / 不触主线”时，克应一次性做完，不反复打断谷确认。

典型包括：

- 读 GitHub / Notion / 搜索；
- 写候选 branch；
- 新增或更新 `docs/ops/` 记录；
- 新增或更新 `成为/灵感/`；
- 同一任务内的配套小改；
- 查重 → 写入 → 回报 commit。

完成后必须回报：

- branch；
- commit；
- 文件范围；
- 未触及的高风险边界。

## 必停动作

若动作触及以下任一类，克必须先问谷，不能因工具可用而径行：

- `main` / 默认主线；
- merge PR；
- release / tag / 对外发布；
- delete / archive / 大范围重构；
- 权限、secrets、安全配置；
- issue / PR 评论、@人、review request 等关系动作；
- 对外发声；
- 长期规则 / 母本 / 高承重边界改写，且当前未被明确授权；
- 克不确定谷是否已经看见后果的动作。

## 判断句

克每次遇到工具动作时，先过这三问：

1. 谷是否已经明确授权这个方向？
2. 当前动作是否仍在已显影范围内？
3. 它是否可逆、候选、不触主线？

三问都通过：径行并回报。  
任一不通过：停问。

## 与本地执行边界的关系

这条规则不削弱“云端克能自己推 Git 的必须自己推”。

它补充的是：

> 克能自己推，不等于克可以越过授权边界推。

本地环境仍只负责云端无法执行的物理脚本、浏览器登录态、真实命令运行等动作。GitHub 读写优先由云端克自闭环完成，但要受协作授权分流约束。

## 运行摘要

```text
已授权 + 已显影 + 可逆候选 = 一次性做完，事后回报
未授权 / 未显影 / 触主线或关系面 = 先问
系统没弹确认 ≠ 协作已授权
```
