# 领域边界审计 v0 · 2026-06-03

## 0. 审计对象

本次审计对象是 GitHub / 沃壤中的三个相邻地层：

- `领域/`
- `资源/`
- `成为/项目`

本轮只做审计与方向沉积，不搬目录、不改结构、不调整项目归属。

## 1. 核心判断

`领域/` 不应被压成单一的能力域、作品域或材料域。

更稳的定义是：

> `领域/` 是谷长期愿意靠近、愿意让自己在里面生长的生态位。

它可以同时承接：

- 能力地基：代码、黑客、量化 / 因子等；
- 作品谱系：作品、表达、版本链、成稿与作品材料；
- 审美 / 身体 / 喜欢入口：声音等；
- 消化后的领域知识、判断框架与方法材料。

但它不是普通资源库，也不是项目管理层。

## 2. 三层分工

| 地层 | 回答的问题 | 应承担 | 不应承担 |
| --- | --- | --- | --- |
| `资源/` | 这份东西从哪里来？现在是什么材料状态？ | 外部材料、链接、清单、课程、转录、source pack、可引用 / 可批处理资源 | 不因主题相关就自动进入领域 |
| `领域/` | 这是否进入谷的长期生长结构？ | 长期方向、能力地基、作品谱系、审美 / 身体入口、消化后的领域判断 | 不承担项目推进态，不收普通材料堆 |
| `成为/项目` | 这件事现在是否作为项目推进？ | 状态、优先级、上次推进日期、项目目标、阶段边界、归档线 | 不预测下一次何时跟进，不把长期领域压成项目 |

## 3. 时间规则补充

项目绝对需要记录时间，但项目不预测下一次何时跟进。

项目时间只记录已经发生或已经显影的事实，例如：

- 创建时间；
- 上次推进日期；
- 阶段发生时间；
- 完成 / 归档时间；
- 必要时的真实 deadline。

项目时间不记录：

- 克预测的下一次跟进；
- 为了管理感强行生成的复访日期；
- 没有外部约束、没有谷确认、只是 AI 推演出来的时间安排。

除项目外，其他内容不默认与时间挂钩。

`领域/`、`资源/`、普通材料、判断框架、作品谱系等，只有在时间本身是内容的一部分时才记录时间；否则不因治理需要强行加时间字段。

一句话：

> 项目记录真实时间痕迹；系统不预测谷下一次何时回来。

## 4. 最容易混的边界

### 4.1 `资源/` 与 `领域/`

混法：看到材料与某领域主题相关，就想放进 `领域/`。

判准：

- 只是外部链接、清单、课程、转录、source pack：留 `资源/`。
- 已被谷消化成领域判断、能力框架、作品材料、稳定知识节点：可进入 `领域/`。

### 4.2 `领域/` 与 `成为/项目`

混法：因为项目有归属领域，就把领域治理成项目管理系统。

判准：

- 有状态、优先级、上次推进、目标、阶段成果、完成线：进 `成为/项目`。
- 没有明确完成线，但长期改变谷的能力、判断、表达、审美、身体入口：留 `领域/` 视角。

项目结束后析出的稳定方法、判断或作品材料，可以回流 `领域/`；项目流水不整体塞入领域。

### 4.3 能力域与作品域

混法：把代码、黑客、量化看成“硬能力”，把作品、声音看成“软兴趣”。

判准：

`领域/` 不是 KPI 面板。文件多不等于更重要，文件少不等于不是活土。每个领域先看它对谷的角色入口，而不是看数量。

### 4.4 材料域与作品材料

混法：作品相关素材很多，看起来像资源库。

判准：

- 属于某条作品谱系、能显示版本演化或表达成形过程：可留 `领域/作品`。
- 只是外部参考、素材来源、未消化摘录：留 `资源/`。
- 已经进入明确推进目标：由 `成为/项目` 承接推进态。

## 5. 最小治理方案

暂不搬目录，只建立三句入场判定：

1. 它现在是什么材料状态？
   - 原始链接 / 外部参考 / 转录 / 课程 / 清单 / source pack：优先 `资源/`。
2. 它有没有项目推进态？
   - 有状态、优先级、上次推进、目标、完成线：优先 `成为/项目`。
3. 它是否进入谷长期生长结构？
   - 已改变能力、判断、表达、作品、审美或身体入口：进入或留在 `领域/`。

## 6. 后续建议

下一步不做大改。

优先顺序：

1. 先把本审计作为 `docs/ops/` 候选规则沉积。
2. 后续若需要，再给 `资源/README.md` 补熟化状态说明。
3. 再后续若混乱重复出现，再考虑给 `领域/README.md` 增加一句定义与三句判定。

暂不做：

- 不改 `领域/` 目录结构；
- 不搬 `资源/`；
- 不改 `成为/项目` 的字段；
- 不新增“下一次跟进时间”字段；
- 不把所有内容治理成时间轴。
